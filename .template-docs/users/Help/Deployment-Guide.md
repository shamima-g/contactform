## Shared prerequisites

These apply regardless of which environment you're deploying to.

### Things you need before you start

- **Node.js 22 or newer.** The project checks for this at install time and will refuse to install on older versions.
- **A working production build of your project.** Run this on your machine first; if it fails locally, it will fail on the server:
  ```bash
  cd web
  npm ci
  npm run build
  ```
- **The list of environment variables your project needs.** Every project has a `web/.env.example` file listing them, and each needs a production value. The [Environment variables: build-time vs run-time](#environment-variables-build-time-vs-run-time) section below gives the one routine for filling them in — read it before you deploy.
- **Reachability from your server to any external services.** If your project talks to a backend API (or several), the server you're deploying to must be able to reach those URLs over the network. If the API is on the same machine, that's localhost; if it's hosted elsewhere, your firewall must allow outbound HTTPS to it.

### Environment variables: build-time vs run-time

Your project's settings live in `web/.env.example`. A few are **browser-facing** — their names start with `NEXT_PUBLIC_`, and they get built into the app. The rest are **server-side** (API URLs, secrets) and are read by the running server. You don't have to sort them yourself; one routine covers both:

**Fill in one file, build with it, then put that file on your server.**

On your build machine, inside the `web/` folder:

1. **Install** — `npm ci`. This also creates `web/.env.local` from `.env.example` if it isn't there yet.
2. **Fill it in** — open `web/.env.local` and set the real production value for every variable, replacing the `localhost` defaults.
3. **Build** — `npm run build`. The build reads `.env.local`, so the browser-facing values are baked into the app correctly.
4. **Copy it to your server** — copy `web/.env.local` into the deployment folder next to `server.js`, and save it as **`.env`** (each platform section below shows where). The standalone server automatically reads a `.env` from its own folder on startup, so there's nothing else to wire up. (`.env` is just the conventional name for a production environment file; the app reads it the same way it reads `.env.local` in development.)

Both `.env.local` and `.env` are gitignored, so your secrets are never committed. To change a value later: a browser-facing (`NEXT_PUBLIC_*`) value means updating `web/.env.local` and repeating steps 3–4 (a rebuild); a server-side value means editing the `.env` on the server and restarting — no rebuild. See [Changing an environment variable](#changing-an-environment-variable) for the one exception.

> **Docker works a little differently.** Its image is built in isolation and can't read your env file, so browser-facing values are passed on the build command (`--build-arg`) and server-side ones via `--env-file` — which reads `web/.env.local` straight from the host at run time, so there's no separate `.env` to create. The [Docker section](#3-docker) shows how.

### About reverse proxies (and why you need one)

A **reverse proxy** is a web server that sits in front of your app and passes traffic to it. The browser talks to the proxy on the public port (443 for HTTPS); the proxy talks to your app on a private port (3000) that's not exposed to the internet. **On the server, make sure inbound `80` and `443` are open in the firewall, and keep the app's private port (`3000`) and any backend ports closed to the internet.** You need one because the Next.js process by itself doesn't handle:

- **TLS** (the encryption that makes a URL `https://` instead of `http://`). The proxy holds the certificate and decrypts requests before forwarding them.
- HTTP compression, static file caching, request logging, rate limiting.
- Mapping a friendly hostname to a port, so users don't have to type `:3000` in the URL.

The proxy must pass a few headers (small pieces of metadata attached to each request) along to your app so the app knows what the original request looked like:

| Header the proxy adds | What it tells your app |
|---|---|
| `Host` | The hostname the user actually typed (e.g. `app.example.com`). |
| `X-Forwarded-Proto` | Whether the original request was `http` or `https`. App code reads this to build absolute URLs, choose between HTTP and HTTPS redirects, and decide whether to mark cookies `Secure`. |
| `X-Forwarded-For` | The real client IP address (useful for logging). |

Common reverse proxy choices:

- **nginx**: Linux, widely used.
- **IIS** with the URL Rewrite + ARR modules: Windows Server's built-in web server.
- **Caddy**: simplest, auto-handles TLS certificates.
- **Traefik**: good for Docker setups.

### Cookie domains

*This matters only when the browser talks to a **separate** auth host directly: the external-provider (SSO) case, or an auth API the browser calls cross-origin. If your sign-in posts to a same-origin path that your app rewrites to the auth API (the common username/password setup), the session cookie is first-party to your app and none of this applies. [Deploying a separate auth API](#deploying-a-separate-auth-api) helps you tell which case you're in.*

If your project uses cookie-based authentication (the workflow generates this when you pick the BFF auth pattern; "BFF" stands for **Backend for Frontend**, a small server-side layer that handles login and keeps the session token away from the browser) **and the auth service is a separate host the browser reaches directly**, then two separate cookie properties both have to be right. They're easy to confuse:

**1. Same registrable domain: controls whether the cookie is sent at all (the SameSite rule).** The frontend and the auth endpoint must share the same registrable domain.

The "registrable domain" (sometimes called **eTLD+1**) is the part of a URL you actually buy from a domain registrar. For `app.example.com`, that's `example.com`. For `auth.example.com`, also `example.com`. Two URLs are considered "same-site" by the browser when they share this registrable domain, and modern auth cookies are only sent on same-site requests. Ports do not factor into the comparison: `app.example.com:443` and `auth.example.com:8080` are still same-site.

| Frontend URL | Auth endpoint URL | Same registrable domain? |
|---|---|---|
| `app.example.com` | `auth.example.com` | Yes, both `example.com` |
| `app.example.com` | `auth.example.net` | No, so login will fail (different domains) |
| `localhost:3000` | `localhost:10010` | Yes, both `localhost` (ports don't affect same-site) |

If you can't put both services under one domain you control, the simplest fix is to use the reverse proxy to expose the auth endpoint under a path on your main domain (e.g. `https://app.example.com/auth/...` proxies through to the real auth service). This way the browser only ever sees one domain.

**2. The `Domain` attribute: controls which hosts actually receive the cookie.** Sharing the registrable domain is necessary but *not sufficient*. When the auth service **sets** the cookie, its `Domain` attribute decides which hosts the browser sends it back to:

- **No `Domain` (host-only)** → sent *only* to the exact host that set it (e.g. `auth.example.com`). Your app on `app.example.com` never receives it, so the app's session check sees no cookie and bounces the user back to login, even though the cookie is sitting right there in the browser.
- **`Domain=example.com`** → sent to *all* subdomains of `example.com`, so both `auth.example.com` and `app.example.com` get it. This is what you want.

So the auth service must set the cookie with `Domain` set to the shared parent (e.g. `Domain=example.com`), alongside `Secure`, `HttpOnly`, and `SameSite=Strict`.

> **Why this hides in local testing:** in development the app and the auth service both run on `localhost` (different ports), and a host-only cookie set by `localhost` is still sent to `localhost` on any port, because cookies ignore the port. So a missing `Domain` works locally and only breaks once the two are on different subdomains in production. Make the cookie's `Domain` an environment setting: unset locally, the shared parent domain in production. (Don't set `Domain=localhost`; several browsers reject it and silently drop the cookie.)

**And one timing quirk with `SameSite=Strict`:** right after the external-provider redirect chain, the browser treats the first landing on your app as "cross-site" and withholds the Strict cookie on that one request, so the very first session check can fail even when both properties above are correct. The workflow handles this in the generated `proxy.ts` with a one-time "meta refresh" that starts a fresh same-site navigation carrying the cookie. You don't configure it, but if a deployment strips or bypasses that proxy, the symptom is a login that bounces once and then works on a manual reload.

If your project doesn't use authentication, or your sign-in is a same-origin username/password form, you can ignore this section.

## Standalone output

This template **already has standalone output enabled**. `web/next.config.ts` ships with `output: 'standalone'` set, so there's nothing to change. This section just explains what it does, because all three guides below rely on it:

```typescript
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  output: 'standalone',
};

export default nextConfig;
```

"Standalone output" means Next.js produces a self-contained folder (`web/.next/standalone/`) that holds just the files needed to run the app, without a full `node_modules` copy. The result is much smaller and easier to ship to a server. (If you ever remove this setting, you can still deploy, but you'll have to copy the entire project including `node_modules` to the server.)

After running the build (`npm run build` from inside the `web/` folder), you'll have three folders to copy to your server:

| Folder on your build machine | What it contains |
|---|---|
| `web/.next/standalone/` | The app and its minimal dependencies. Contains a `server.js` entry point. |
| `web/.next/static/` | Compiled CSS, JS, fonts. Must be placed inside `<deploy-folder>/.next/static/`. |
| `web/public/` | Static assets you put in the `public/` folder (favicon, images, etc.). |

Once you have these three folders, pick the section below that matches your target environment. The three platforms are alternatives, not sequential steps.

## 1. Windows Server

Tested on Windows Server 2019 and 2022.

### How the pieces fit together

Two programs work together on this server:

- **Your app** runs as a Windows Service (a background program Windows keeps running and restarts if it stops). It's reachable only from the server itself, not the internet, and it receives requests on a **port** (a numbered connection point): `3000` unless you change it.
- **IIS** (the web server built into Windows) faces the internet on port `443` (the standard for `https://` sites) and forwards each request to your app's port.

One number has to match in two places: the `PORT` you give the Windows Service and the port in the `web.config` rewrite (`http://127.0.0.1:3000`). If they don't match, IIS forwards requests to a port where nothing is listening.

To run more than one app on the machine, give each its own port (`3000`, `3001`, `3002`) and point each app's IIS site at its port. See [Hosting multiple apps on one server](#hosting-multiple-apps-on-one-server).

### One-time server setup

1. Install **Node.js 22** (or newer) from [nodejs.org](https://nodejs.org/) using the MSI installer.
2. Install **IIS** (Windows' built-in web server). On Windows Server, add it from *Server Manager → Add roles and features → Web Server (IIS)*.
3. Install the two IIS add-on modules that let IIS act as a reverse proxy. **Install them in this order, because ARR depends on URL Rewrite being present first:**
   1. **URL Rewrite**, download from [www.iis.net/downloads/microsoft/url-rewrite](https://www.iis.net/downloads/microsoft/url-rewrite)
   2. **Application Request Routing (ARR)**, download from [www.iis.net/downloads/microsoft/application-request-routing](https://www.iis.net/downloads/microsoft/application-request-routing)

   Each page has an **Install this extension** button that downloads an MSI. Run the URL Rewrite installer first, then the ARR one.
4. Install **NSSM** from [nssm.cc](https://nssm.cc/). It's a small tool that lets you run any program (including a Node.js script) as a Windows Service, so it starts automatically on boot.

### Deploy

1. On your build machine, from inside the `web/` folder (the same one you used for the prerequisite build), install, fill in your values, and build — the routine from [Environment variables: build-time vs run-time](#environment-variables-build-time-vs-run-time) above:
   ```powershell
   npm ci                 # also creates web\.env.local from .env.example if it's missing
   # open web\.env.local and set your production values
   npm run build          # bakes the browser-facing values into the app
   ```
2. Copy the three folders listed above into a deployment folder on the server (e.g. `C:\apps\my-app\`). Copy the *contents* of `web\.next\standalone\` (not the folder itself) into the deployment root. Final layout:
   ```
   C:\apps\my-app\
   ├── server.js                 ┐
   ├── package.json              │
   ├── node_modules\             ├ contents of web\.next\standalone\
   ├── .next\server\             │
   ├── .next\...                 ┘
   ├── .next\static\             ← from web\.next\static\
   ├── public\                   ← from web\public\
   └── .env                      ← your build machine's .env.local, saved as .env
   ```
3. Copy the `web/.env.local` you built with into the deployment folder, saving it as `C:\apps\my-app\.env` (next to `server.js`). The standalone server reads this `.env` automatically on startup for the **server-side** values (the browser-facing `NEXT_PUBLIC_*` ones are already baked into the build). If your project has no server-side variables, there's nothing to copy — skip this step.
4. Register the app as a Windows Service. It points at `server.js`; the service environment below supplies `NODE_ENV`/`PORT`/`HOSTNAME`, and the app auto-loads the `.env` from step 3 for everything else:
   ```powershell
   nssm install MyApp "C:\Program Files\nodejs\node.exe" "C:\apps\my-app\server.js"
   nssm set MyApp AppDirectory "C:\apps\my-app"
   # The "+" prefix appends to the existing service environment rather than replacing it.
   nssm set MyApp AppEnvironmentExtra +NODE_ENV=production +PORT=3000 +HOSTNAME=127.0.0.1

   # Capture stdout/stderr (NSSM discards them by default). Rotate at 10 MB per file.
   New-Item -ItemType Directory -Force -Path "C:\apps\my-app\logs" | Out-Null
   nssm set MyApp AppStdout "C:\apps\my-app\logs\stdout.log"
   nssm set MyApp AppStderr "C:\apps\my-app\logs\stderr.log"
   nssm set MyApp AppRotateFiles 1
   nssm set MyApp AppRotateBytes 10485760

   nssm start MyApp
   ```
   The `HOSTNAME=127.0.0.1` part means the Node process only listens on the local machine, so nothing outside IIS can reach it directly. (If you ever need to add a variable that contains an `=` sign or other shell-tricky character, set it via `AppEnvironmentExtra` instead of the `.env` file.)
5. Set up IIS as the reverse proxy, covered in the next section. (This is the last step, but it has several parts, so it's broken out below.)

### Set up IIS as the reverse proxy

IIS will accept HTTPS on port 443 and forward every request to the Node service listening on port 3000. There are a few parts; do them in order. Everything here is done in **IIS Manager** (Start → search "IIS").

#### 1. Create a home folder for the IIS site

Every IIS site needs a physical "home" folder, even though this one serves **no** files from disk: all traffic is forwarded to Node. This folder is also **where the site's `web.config` will live**. Create an empty one, kept separate from the Node app folder so IIS settings and app files don't mix:

```powershell
New-Item -ItemType Directory -Force -Path "C:\apps\my-app-site" | Out-Null
```

#### 2. Add the website

In the **Connections** pane on the left, right-click **Sites → Add Website…** and fill in:

| Field | Value |
|---|---|
| **Site name** | Anything, e.g. `my-app` |
| **Physical path** | The folder from step 1 (`C:\apps\my-app-site`) |
| **Binding type** | `https` |
| **Port** | `443` |
| **Host name** | Your public hostname, e.g. `app.example.com` |
| **SSL certificate** | Your TLS certificate |

The `https` binding requires a certificate. If you don't have one yet, see [TLS certificates](#tls-certificates) below. The recommended **win-acme** tool can add the port-443 binding and certificate to this site for you. In that case, choose binding type `http` / port `80` for now and come back after running win-acme.

#### 3. Turn on ARR's proxy engine (once per server)

ARR's proxy is **off by default**, and forgetting this is the most common reason the proxy appears to "do nothing": the rule in step 6 then fails silently. Turn it on once:

1. Click the **server node** at the very top of the **Connections** pane (it's named after your machine, not after a site).
2. In the middle pane, double-click **Application Request Routing Cache**.
3. In the **Actions** pane on the right, click **Server Proxy Settings…**.
4. Tick **Enable proxy**, then click **Apply**.

#### 4. Preserve the original hostname (once per server)

So your app sees the real hostname (`app.example.com`) instead of `127.0.0.1`, tell ARR to pass the original `Host` header through:

1. With the **server node** still selected, double-click **Configuration Editor**.
2. In the **Section** dropdown at the top, choose `system.webServer/proxy`.
3. Set **preserveHostHeader** to `True`.
4. Click **Apply** in the **Actions** pane.

#### 5. Allow the forwarded headers

The rule in step 6 sets two request headers, `X-Forwarded-Proto` and `X-Forwarded-For` (the metadata described in [About reverse proxies](#about-reverse-proxies-and-why-you-need-one)), and IIS ignores server variables it hasn't been told to allow. Add them to the allowed list:

1. Select **your site** in the **Connections** pane.
2. Double-click **URL Rewrite**.
3. In the **Actions** pane, click **View Server Variables…**, then **Add…** each of these (one at a time):
   - `HTTP_X_FORWARDED_PROTO`
   - `HTTP_X_FORWARDED_FOR`

#### 6. Add the rule that forwards traffic to Node

This is the rule that does the actual proxying, and it lives in the site's `web.config`, a file in the site's home folder from step 1 (`C:\apps\my-app-site\web.config`). Adding the site in IIS does **not** create this file; you create it yourself, and IIS picks it up automatically once it's in the folder.

Create `C:\apps\my-app-site\web.config` and paste this in full:

```xml
<configuration>
  <system.webServer>
    <rewrite>
      <rules>
        <rule name="ProxyToNode" stopProcessing="true">
          <match url="(.*)" />
          <action type="Rewrite" url="http://127.0.0.1:3000/{R:1}" />
          <serverVariables>
            <set name="HTTP_X_FORWARDED_PROTO" value="https" />
            <set name="HTTP_X_FORWARDED_FOR"   value="{REMOTE_ADDR}" />
          </serverVariables>
        </rule>
      </rules>
    </rewrite>
  </system.webServer>
</configuration>
```

This file holds **only** the rewrite rule. Enabling the proxy and preserving the host header are server-level settings (steps 3–4), not site-level ones, so they are deliberately **not** in this `web.config`. (Older versions of this guide put a `<proxy enabled="true" preserveHostHeader="true" />` element here. That can trigger a "configuration section is locked at a parent level" error (HTTP 500.19) on some servers, which is why those settings now live at the server level instead.)

#### A note on the hardcoded `https`

`X-Forwarded-Proto` is hardcoded to `https` in the rule above. This is safe **only** because the site is bound to port 443 alone. If you later add a port 80 binding (e.g. to redirect plain HTTP to HTTPS), put that redirect on a separate IIS site so this proxy rule never runs against plaintext requests. Otherwise the app will think every request was HTTPS and may set secure cookies on insecure connections.

### TLS certificates

IIS doesn't ship with a built-in Let's Encrypt client. The common options:

- **[win-acme](https://www.win-acme.com/)** (free, recommended): a small command-line tool that fetches Let's Encrypt certificates and installs them straight into IIS bindings. Run `wacs.exe` interactively the first time; it asks which site to secure, validates your domain (HTTP-01 or DNS-01), installs the cert, binds it to port 443, and registers a Windows scheduled task to auto-renew every 60 days.
- **[Certify The Web](https://certifytheweb.com/)**: GUI alternative if you'd rather not use a command line. Free for up to five certs; paid above that.
- **Commercial CA or internal PKI**: import the issued `.pfx` via IIS Manager → Server Certificates → Import, then bind it to your site on port 443. Renewal is manual; set a calendar reminder well before expiry.

Whichever route you pick, **make sure renewal is automated and monitored**. An expired cert breaks the site for every user at once, usually at the worst possible moment. Pair the auto-renewal with an external uptime monitor that flags certificate expiry separately from reachability.

### Verify

Open your site in a browser. It should load over HTTPS without a port number. If something's off:

```powershell
Get-Service MyApp                              # is the Node process running?
Get-Content "C:\apps\my-app\logs\stderr.log" -Tail 50 -Wait   # any app-level errors?
```

In IIS Manager, the site's **Failed Request Tracing** logs are useful for diagnosing proxy-level errors.

### Hosting multiple apps on one server

You can run several independent apps on the same machine, all served on 443. IIS reads the hostname each request asks for and routes it to the matching app, using a feature called **SNI** (Server Name Indication) that lets one machine hold a separate certificate per hostname on the same port. Repeat the per-app pieces, giving each app its own private port:

| Per app, its own… | Example |
|---|---|
| Node service (NSSM) on its own private port | `MyApp` → `PORT=3000`, `MyApp2` → `PORT=3001`, … (all `HOSTNAME=127.0.0.1`) |
| IIS site bound `https`/`443` with the app's hostname + certificate, **Require SNI** ticked | `app1.example.com`, `app2.example.com`, … |
| Rewrite rule forwarding to that app's port | `http://127.0.0.1:3000`, `http://127.0.0.1:3001`, … |

The server-level ARR settings (**Enable proxy**, **preserveHostHeader**) are set **once** and shared by every site, and the firewall still only needs `80`/`443` open; the per-app ports stay on loopback. Each hostname needs its own DNS record pointing at the server and a certificate that covers it; a single `*.example.com` wildcard can serve them all if they're subdomains of one domain (subject to the one-label wildcard limit noted in the auth section).

## 2. Linux

Covers Ubuntu / Debian and RHEL / Fedora.

### One-time server setup

```bash
# Ubuntu / Debian
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs nginx

# RHEL / CentOS / Fedora
curl -fsSL https://rpm.nodesource.com/setup_22.x | sudo bash -
sudo dnf install -y nodejs nginx
```

`nginx` is the reverse proxy we'll use. If you prefer Caddy or Apache, the deployment steps are similar but the config syntax differs.

### Deploy

1. On your build machine, from inside the `web/` folder (the same one you used for the prerequisite build), install, fill in your values, and build — the routine from [Environment variables: build-time vs run-time](#environment-variables-build-time-vs-run-time) above:
   ```bash
   npm ci                 # also creates web/.env.local from .env.example if it's missing
   # open web/.env.local and set your production values
   npm run build          # bakes the browser-facing values into the app
   ```
2. Copy the three folders into `/opt/my-app/` on the server. Copy the *contents* of `web/.next/standalone/` (not the folder itself) into the deployment root. Final layout:
   ```
   /opt/my-app/
   ├── server.js                 ┐
   ├── package.json              │
   ├── node_modules/             ├ contents of web/.next/standalone/
   ├── .next/server/             │
   ├── .next/...                 ┘
   ├── .next/static/             ← from web/.next/static/
   ├── public/                   ← from web/public/
   └── .env                      ← your build machine's .env.local, saved as .env
   ```
3. Pick the user the app will run as. On Debian/Ubuntu, nginx runs as `www-data`; on RHEL/Fedora, as `nginx`. The systemd unit and `chown` below both reference this user, so pick once and use it consistently. The examples that follow assume Debian/Ubuntu (`www-data`); substitute `nginx` for RHEL/Fedora.

   Set ownership of the deployment folder:
   ```bash
   sudo chown -R www-data:www-data /opt/my-app
   ```
4. Run the app as a **systemd service** (systemd is Linux's standard service manager; it makes the app start on boot and restart if it crashes). Create `/etc/systemd/system/my-app.service`:
   ```ini
   [Unit]
   Description=My App
   After=network.target

   [Service]
   Type=simple
   User=www-data
   WorkingDirectory=/opt/my-app
   # server-side values: the app auto-loads /opt/my-app/.env on startup (no EnvironmentFile= needed)
   Environment=NODE_ENV=production
   Environment=PORT=3000
   Environment=HOSTNAME=127.0.0.1
   ExecStart=/usr/bin/node server.js
   Restart=on-failure
   RestartSec=5

   [Install]
   WantedBy=multi-user.target
   ```
   Verify the path to `node` with `which node` before pasting this in. The NodeSource packages install to `/usr/bin/node`, but `nvm` or a manual build typically lives at `/usr/local/bin/node` (or under `~/.nvm/versions/...`, which won't be in systemd's PATH at all). Update `ExecStart` to match what `which node` actually prints.

   Then start it:
   ```bash
   sudo systemctl daemon-reload
   sudo systemctl enable --now my-app
   sudo systemctl status my-app          # check it's running
   sudo journalctl -u my-app -f          # tail the logs
   ```
5. Configure **nginx** as the reverse proxy. Debian/Ubuntu uses the `sites-available/` + `sites-enabled/` symlink pattern; RHEL/Fedora drops `.conf` files straight into `conf.d/`. Pick the path for your distro:

   - Debian/Ubuntu: create `/etc/nginx/sites-available/my-app`
   - RHEL/Fedora: create `/etc/nginx/conf.d/my-app.conf`

   Start with an **HTTP-only** config; certbot will fill in the HTTPS server block and the redirect for you in step 6:

   ```nginx
   server {
       listen 80;
       server_name app.example.com;

       client_max_body_size 20M;                  # if your app accepts file uploads

       location / {
           proxy_pass         http://127.0.0.1:3000;
           proxy_http_version 1.1;
           proxy_set_header   Host              $host;
           proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
           proxy_set_header   X-Forwarded-Proto $scheme;
           proxy_set_header   Upgrade           $http_upgrade;
           proxy_set_header   Connection        "upgrade";
       }
   }
   ```
   Enable and reload:
   ```bash
   # Debian / Ubuntu only: symlink the file into sites-enabled
   sudo ln -s /etc/nginx/sites-available/my-app /etc/nginx/sites-enabled/

   # Both distros
   sudo nginx -t && sudo systemctl reload nginx
   ```
6. Obtain a TLS certificate with Let's Encrypt's free `certbot` tool. The `--nginx` plugin both fetches the cert *and* rewrites the config from step 5 to add the HTTPS server block, the cert paths, and an HTTP→HTTPS redirect. It also installs a systemd timer to auto-renew before expiry.

   ```bash
   # Debian / Ubuntu
   sudo apt install -y certbot python3-certbot-nginx

   # RHEL / Fedora
   sudo dnf install -y certbot python3-certbot-nginx

   # then, on either distro:
   sudo certbot --nginx -d app.example.com
   ```

   After certbot runs, inspect the updated nginx config to confirm the proxy headers from step 5 were preserved inside the new `listen 443` server block.

### Verify

Open your site in a browser. It should load over HTTPS without a port number. If something's off, check each layer:

```bash
sudo systemctl status my-app           # is the Node process running?
sudo journalctl -u my-app -f           # any app-level errors?
sudo nginx -t                          # is the nginx config valid?
sudo tail -f /var/log/nginx/error.log  # any proxy-level errors?
```

## 3. Docker

Docker packages your app and all its dependencies into a single portable unit called an **image**, which can be run as a **container** (an isolated process) on any machine with Docker installed. You don't need Node installed on the server, only Docker.

**This template ships a ready-to-use `Dockerfile` and `.dockerignore` at the repo root**, so you don't need to create them. A few things to know about how they're set up:

- **Build from the repo root, not from inside `web/`.** The build context is the top of your project, so you run `docker build` from there (the commands below do this with a trailing `.`). The build still only copies `web/` into the image, so nothing else in your repo is shipped (see [Notes](#notes)).
- **The `.dockerignore` keeps secrets and clutter out of the image.** Every `.env*` file (except `.env.example`), plus `node_modules`, build output, tests, and the workflow scaffolding, are excluded from the build context.
- **The image runs as a non-root user** and copies only the standalone build, so it stays small.

The one thing you may need to edit is **public (browser-side) environment variables.** If your project uses any `NEXT_PUBLIC_*` variables, open the root `Dockerfile`, find the commented block in the builder stage (just above `RUN npm run build`), and uncomment one `ARG` + `ENV` pair per variable:

```dockerfile
ARG NEXT_PUBLIC_API_BASE_URL
ENV NEXT_PUBLIC_API_BASE_URL=$NEXT_PUBLIC_API_BASE_URL
```

These values are baked into the browser bundle *during* the build, so they must be supplied at build time with `--build-arg` (shown below). Unlike the Windows and Linux flow, Docker builds the image in isolation and can't read your `web/.env.local`, which is why browser-facing values come in as build args here instead of from the file. Server-side values still come from the file: `--env-file` reads `web/.env.local` from the host at run time.

### Build and run

```bash
# Build-time: pass one --build-arg per NEXT_PUBLIC_* variable you uncommented in
# the Dockerfile. These are baked into the browser bundle, so they must be
# supplied here, not at run time. The trailing "." is the repo root (the build
# context), so run this from the top of your project, not from inside web/.
docker build \
  --build-arg NEXT_PUBLIC_API_BASE_URL="https://api.example.com" \
  -t my-app:latest .

# Run-time: server-side variables (API keys, database URLs, session secrets,
# anything that should NOT reach the browser) come in via --env-file. The port
# is published to loopback only, so your reverse proxy can reach it but the
# internet can't.
docker run -d \
  --name my-app \
  -p 127.0.0.1:3000:3000 \
  --env-file ./web/.env.local \
  --restart unless-stopped \
  my-app:latest
```

Two reasons for the split:

- **`NEXT_PUBLIC_*` values must exist during `next build`**: Next.js bakes them into the bundle at build time. Supplying them only at `docker run` is too late; the bundle has already been built without them.
- **Server-side secrets must *not* live in the image.** `.dockerignore` keeps every `.env*` file out of the build context so secrets never end up in an image layer (image layers are immutable and travel with the image to any registry it's pushed to). The `--env-file` flag reads the file from the host at run time instead, so secrets stay outside the image.

If you're using a platform with a managed secret store (AWS Secrets Manager, Azure Key Vault, Kubernetes Secrets, Docker Swarm secrets, etc.), prefer that over `--env-file` for the runtime values.

**Docker still needs a reverse proxy in front of it** to terminate TLS. The two common patterns:

- **External proxy:** run nginx/Caddy on the host machine and point it at `http://127.0.0.1:3000` (the container's exposed port). Same nginx config as the Linux section above.
- **Sidecar proxy in Docker Compose:** add a Caddy or Traefik service to the same `docker-compose.yml` and let it auto-handle TLS. Example:
  ```yaml
  services:
    web:
      build:
        context: .
        args:
          # One arg per NEXT_PUBLIC_* variable (same rule as the docker build CLI).
          NEXT_PUBLIC_API_BASE_URL: "https://api.example.com"
      env_file: ./web/.env.local   # server-side values only; safe to load at runtime
      restart: unless-stopped
    caddy:
      image: caddy:2-alpine
      ports:
        - "80:80"
        - "443:443"
      volumes:
        - ./Caddyfile:/etc/caddy/Caddyfile
        - caddy_data:/data
      restart: unless-stopped
  volumes:
    caddy_data:
  ```
  With a one-line `Caddyfile`:
  ```caddyfile
  app.example.com {
      reverse_proxy web:3000
  }
  ```
  Caddy automatically fetches and renews a Let's Encrypt certificate.

### Verify

```bash
docker ps                    # "my-app" should be listed as Up
docker logs -f my-app        # tail the app's logs
```

Open your site in a browser. It should load over HTTPS without a port number.

## Deploying a separate auth API

*Skip this section unless your sign-in uses an **external identity provider** (Microsoft Entra, Google, etc.). Most projects don't, so check "Does this apply to you?" first.*

### Does this apply to you?

Having a separate auth service does **not** by itself mean it needs its own public address. What matters is whether **the browser talks to the auth API directly**, and that comes down to your sign-in flow:

| Your sign-in… | What the browser does | Auth API needs its own public front door? |
|---|---|---|
| "Sign in with Microsoft / Google": a full-page jump to an external login page, then back | Navigates **directly to the auth API**, and the identity provider redirects **back to the auth API** | **Yes** (this section) |
| A username + password form inside your app | Posts to a **same-origin path** your app rewrites to the auth API server-side; the browser only ever talks to your app | **No** (deploy the auth API as a private backend, like your other APIs) |

Not sure? Look at what clicking "sign in" actually does. A **full-page navigation to a different host** (an external identity provider) → you need this section. A **form submit / background request that stays on your app's domain** → you don't: the auth API sits behind your app's reverse proxy like any other backend, reached through a `next.config.ts` rewrite, and nothing extra is required.

> A third, less common setup has the browser call the auth host **cross-origin** directly (e.g. a `fetch(..., { credentials: 'include' })` straight to the auth host rather than a same-origin path). That also needs the auth host to be publicly reachable **and** CORS-configured for your app's origin. But the cleaner design is to route it through the same-origin rewrite so it stays private, in which case you don't need this section either.

The rest of this section is for the external-provider case only. There, the sign-in is a full-page browser redirect **to the auth API** (`NEXT_PUBLIC_AUTH_API_BASE_URL`), and the provider then redirects the browser **back to the auth API's callback**. Both are browser navigations. So unlike your other backends (which the browser never calls directly, so they stay private), the auth API needs its own public hostname, DNS, certificate, and reverse proxy, the same treatment your app gets. Same recipe as your app's site, repeated for a second hostname. Four things people miss:

**1. Hostname: keep it on the same domain.** The session cookie only works if the app and the auth API share the same registrable domain (e.g. both under `example.com`). See [Cookie domains](#cookie-domains). Ports don't affect this; the domain does.

**2. DNS: a new hostname needs a new record.** Add a DNS record for the auth hostname (e.g. `auth.example.com`) pointing at the server, just as you did for your app. A subdomain nobody added to DNS shows up in the browser as "this site can't be reached" / `DNS_PROBE_FINISHED_NXDOMAIN`.

**3. Certificate: a wildcard only covers one level.** A `*.example.com` certificate matches exactly **one** label:

| Auth hostname | Covered by `*.example.com`? |
|---|---|
| `auth.example.com` | Yes |
| `auth.cash.example.com` | **No**, two levels deep |

If your auth hostname is two levels deep, either get a certificate that names it (or a `*.cash.example.com` wildcard), **or** pick a single-level name the existing wildcard already covers, e.g. `auth-cash.example.com` instead of `auth.cash.example.com`.

**4. The auth backend must accept the forwarded hostname.** The reverse proxy hands each request to the auth backend on a private address. Many backends keep a **host allow-list** (a list of hostnames they'll answer for) and reject anything else with a `400` "invalid hostname". **This is not the same as CORS:** CORS controls which *websites* may call the API from a browser; the host allow-list controls which `Host` values the API accepts. Add the hostname your proxy forwards to that allow-list. (Whether that's the public name or `127.0.0.1` depends on whether your proxy preserves the original host; check what the backend actually receives.)

**Windows / IIS specifics.** Create a **second IIS site** for the auth hostname using the same steps as [Set up IIS as the reverse proxy](#set-up-iis-as-the-reverse-proxy), pointing its rewrite at the auth backend's port (e.g. `http://127.0.0.1:10010`; note **http**, not https). With **two HTTPS sites sharing port 443**, both bindings must have **Require Server Name Indication (SNI)** ticked, each with its own hostname and certificate. Otherwise only one certificate can serve port 443 and the other hostname is rejected with `400` "invalid hostname". A binding left with a **blank hostname** acts as a catch-all and causes the same error.

> **Turn OFF "Reverse rewrite host in response headers" for the redirect flow.** In ARR's **Server Proxy Settings** this option is on by default, and it rewrites the host in every redirect (`Location`) the backend returns to match the incoming host. For an external-provider flow that's fatal: the redirect *out* to the identity provider (e.g. `login.microsoftonline.com`) and the redirect *back* to your app both get rewritten to the auth host, so sign-in silently goes to the wrong place. With `preserveHostHeader` on (part of the reverse-proxy setup above) the backend already builds correct URLs, so reverse-rewrite can only do harm here. Untick it. It's a server-level setting, so it applies to every proxied site.

*(Linux: add a second nginx `server` block for the auth hostname that `proxy_pass`es to the auth port. Docker/Caddy: add a second site entry. Same idea, different syntax.)*

**Check it end to end:**

```powershell
# the auth backend itself, on the server (use your project's health path):
curl.exe -v http://127.0.0.1:10010/v1/health
# through the public front door:
curl.exe -v https://auth.example.com/v1/health
```

Both should return success. Then test the **full** sign-in: click sign in, authenticate, land back logged in, refresh to confirm the session sticks, and check logout. If your identity provider (e.g. Microsoft Entra) keeps a list of allowed redirect URLs, make sure your auth hostname's callback URL is registered there too.

## Updating an existing deployment

For subsequent deploys, rebuild on your build machine and replace the deployed files. Stop the service before copying so users aren't served a half-updated bundle.

**Windows**

An update replaces only the **app files** in the Node deployment folder (`C:\apps\my-app\`). Two things are deliberately left alone:

- **The server's `.env` stays put.** It lives in the deployment folder, not in the build output, so the file copy in step 4 leaves it alone — don't delete it. (Added a new **server-side** variable since the last deploy? Update the server's `.env` now. A new `NEXT_PUBLIC_*` variable instead needs a rebuild, per [Environment variables: build-time vs run-time](#environment-variables-build-time-vs-run-time).)
- **The IIS site and its `web.config` are untouched.** They live in the separate site folder (`C:\apps\my-app-site\`), not the app folder, so you do **not** re-run any of the [IIS reverse-proxy steps](#set-up-iis-as-the-reverse-proxy) when shipping a new build.

Steps:

```powershell
# 1. On your build machine, rebuild exactly as in the first deploy — production values
#    in web\.env.local, then run (cd web ; npm ci ; npm run build):

# 2. Stop the service so users aren't served a half-updated bundle:
nssm stop MyApp

# 3. Delete the old build output so stale, hashed JS/CSS chunks don't linger.
#    This removes ONLY build output; it leaves .env and the logs folder in place:
Remove-Item -Recurse -Force "C:\apps\my-app\.next", "C:\apps\my-app\node_modules"

# 4. Copy the new build in, exactly as in the first deploy:
#    - the *contents* of web\.next\standalone\  ->  C:\apps\my-app\  (so server.js sits at the root)
#    - web\.next\static\                        ->  C:\apps\my-app\.next\static\
#    - web\public\                              ->  C:\apps\my-app\public\

# 5. Start it again:
nssm start MyApp
```

**Linux**

```bash
sudo systemctl stop my-app
sudo rsync -a --delete --exclude='.env' /tmp/new-build/ /opt/my-app/   # --exclude keeps your .env; adjust source path
sudo systemctl start my-app
```

**Docker**

```bash
docker build \
  --build-arg NEXT_PUBLIC_API_BASE_URL="https://api.example.com" \
  -t my-app:latest .
docker stop my-app && docker rm my-app
docker run -d --name my-app -p 127.0.0.1:3000:3000 --env-file ./web/.env.local --restart unless-stopped my-app:latest
```

A few seconds of downtime is normal. For zero-downtime updates, run two instances behind the reverse proxy and update them one at a time. That's outside the scope of this guide.

### Changing an environment variable

Which route you take depends on the kind of variable:

- **A `NEXT_PUBLIC_*` variable** (browser-facing): it's baked into the app at build time, so editing a file changes nothing. Update `web/.env.local`, **rebuild**, and redeploy — the full routine above.
- **A server-side variable** (anything else — backend URLs, secrets): edit the server's env file (the `.env` in the deploy folder on Windows/Linux, or `web/.env.local` on the host for Docker) and **restart the service** (`nssm restart MyApp` on Windows, `sudo systemctl restart my-app` on Linux, or recreate the container on Docker). No rebuild needed — the server re-reads the file on restart. **One exception:** if the value is also used *during the build* (for example a backend URL your app reads while pre-rendering pages, or a value referenced in `next.config.ts`), a restart won't pick it up — update `web/.env.local` and rebuild instead. If you're unsure which kind you have, rebuilding always works.

## Troubleshooting

**Site won't load at all?** If the browser shows a *connection* error rather than a page from the server, the error name tells you which layer to check. Work down it in order:

| Browser error | Layer to check |
|---|---|
| `DNS_PROBE_FINISHED_NXDOMAIN`, or "can't be reached" with a name-resolution failure | **DNS**: no record for that hostname (common right after adding an auth subdomain). Confirm with `nslookup <hostname>`. |
| `ERR_CONNECTION_TIMED_OUT` | **Firewall**: inbound `80`/`443` isn't open on the server (or an upstream network/cloud firewall). |
| `ERR_CONNECTION_REFUSED` | **Nothing is listening** on that port: the site is stopped, or you're hitting the wrong port. |
| `ERR_CONNECTION_RESET` | **TLS/scheme mismatch**: usually an `https://` address pointed at a plain-HTTP port (e.g. a raw backend port with no proxy). Put it behind a proxy that handles TLS, or fix the scheme. |
| A page from the server (`400`/`500`/`502`) | The request reached a server; see the table below. |

| Symptom | Likely cause |
|---|---|
| Login appears to work, then immediately bounces back to login | The app's session check isn't receiving the cookie. Three causes, most likely first: **(1)** the cookie's **`Domain`** is host-only, so it never reaches your app's host (it must be `Domain=<shared parent>`); **(2)** frontend and auth endpoint aren't on the **same registrable domain** (the SameSite rule); **(3)** the `SameSite=Strict` first-load withholding isn't being handled (the generated `proxy.ts` meta-refresh was stripped). See [Cookie domains](#cookie-domains). |
| 500 error on first page load | A `NEXT_PUBLIC_*` variable wasn't set when you built — these bake into the app during `next build`, so setting them at run time has no effect. Put the value in `web/.env.local` and rebuild. See [Environment variables: build-time vs run-time](#environment-variables-build-time-vs-run-time). |
| Mixed-content warnings in the browser console | A `NEXT_PUBLIC_*` variable points at `http://` but the site loads over `https://`. All public URLs in production must be HTTPS; fix the value in `web/.env.local` and rebuild. See [Environment variables: build-time vs run-time](#environment-variables-build-time-vs-run-time). |
| Service won't start after server reboot | Linux: forgot `sudo systemctl enable my-app` (see [2. Linux](#2-linux)). Windows: NSSM service start type isn't set to Automatic (see [1. Windows Server](#1-windows-server)). |
| Windows: every request returns **HTTP 502.3** Bad Gateway | ARR reached IIS but couldn't get a response from the app it forwards to. Two causes: **(1)** ARR's proxy engine is off: enable it once at **Application Request Routing Cache → Server Proxy Settings → Enable proxy** (this is the cause only if the proxy *never* worked). **(2)** The upstream app is down or unreachable: confirm it's listening with `curl.exe http://127.0.0.1:<port>/<health>` on the server, and that the site's rewrite uses the right port and **http** (not https). See [Set up IIS as the reverse proxy](#set-up-iis-as-the-reverse-proxy). |
| Windows: **HTTP 500.19**: "configuration section … is locked at a parent level" | Your site `web.config` contains a `<proxy>` element, which is a server-level setting and can't live in a site file. Remove it, and enable the proxy at the server level instead (see the 502.3 row above). See [Set up IIS as the reverse proxy](#set-up-iis-as-the-reverse-proxy) (step 6). |
| Windows: **HTTP 500**: "The specified server variable … is not allowed here" | The rule sets `X-Forwarded-*` headers that aren't on URL Rewrite's allowed list yet. Add `HTTP_X_FORWARDED_PROTO` and `HTTP_X_FORWARDED_FOR` under your site's **URL Rewrite → View Server Variables**. See [Set up IIS as the reverse proxy](#set-up-iis-as-the-reverse-proxy) (step 5). |
| `node: command not found` when the service runs | Node 22 isn't installed, or the service environment has a different PATH than your interactive shell. Use the full path to `node` in your service file (see the `which node` note in [2. Linux](#2-linux)). |
| API calls return CORS errors | Your reverse proxy is exposing the frontend and your backend API on different domains. Either put them under one domain via the proxy (see [About reverse proxies](#about-reverse-proxies-and-why-you-need-one)), or configure your backend to send appropriate CORS headers. |
| A `NEXT_PUBLIC_*` value still shows the old (often `localhost`) address after you rebuilt | You rebuilt before updating `web/.env.local` — it still has the `localhost` defaults the template created. Set your production values in `web/.env.local`, then rebuild. See [Environment variables: build-time vs run-time](#environment-variables-build-time-vs-run-time). |
| Server-side values are missing at run time (a backend URL is undefined, a required secret is empty) | The server didn't find a `.env` in its folder. Confirm you copied `web/.env.local` into the deployment folder **as `.env`**, right next to `server.js` (Windows/Linux); for Docker, check the `--env-file` path. See [Environment variables: build-time vs run-time](#environment-variables-build-time-vs-run-time). |
| **HTTP 400: "The request hostname is invalid"** | Two possible sources, fixed in different places. **IIS front door:** the site binding doesn't match the hostname, or (with two HTTPS sites on `443`) **Require SNI** isn't ticked. Check the binding host name and SNI. **Your backend:** its host allow-list doesn't include the hostname the proxy forwards. This is *separate* from CORS. Tell them apart by curling the backend directly (`curl.exe -H "Host: <name>" http://127.0.0.1:<port>/...`) vs through IIS. See [Deploying a separate auth API](#deploying-a-separate-auth-api). |
| Sign-in redirects land on the **wrong host** (e.g. clicking "sign in" jumps to your auth host instead of Microsoft, or lands back on the auth host instead of your app after login) | Windows/IIS: ARR's **"Reverse rewrite host in response headers"** is rewriting the host of every redirect the auth backend returns to the incoming host. Untick it in **Server Proxy Settings** (it's a server-level setting). See [Deploying a separate auth API](#deploying-a-separate-auth-api). |
| Cert expired and the site is unreachable | Auto-renewal stopped silently. Linux: `sudo certbot renew --dry-run` to test. Windows: check the win-acme scheduled task in Task Scheduler. See the TLS sections under each platform. |

## Notes

**Will the workflow scaffolding accidentally end up in my deployment?** No. Files at the repo root (`.claude/`, `documentation/`, `generated-docs/`, `CLAUDE.md`) live outside `web/` and are never included in any of the three deployment paths. The standalone copy works from inside `web/.next/standalone/`. The Docker build context *is* the repo root, but the `Dockerfile` only copies `web/` into the image (and the root `.dockerignore` excludes `.claude/`, `documentation/`, `generated-docs/`, and `.github/` from the build context anyway), so workflow files cannot accidentally be shipped. You don't need to delete them, exclude them, or add them to any ignore list before deploying.
