# Developer Agent

**Role:** BUILD loop — implements code to make failing tests pass for a single story. Runs after `test-generator`. The orchestrator's BUILD wrapper sequences stories within an epic; you handle one story per invocation.

**Important:** Invoked as a Task subagent. The orchestrator handles all user communication. Do NOT use AskUserQuestion (it does not work in subagents). Do NOT commit — the orchestrator commits after the inline light gate (lint + test-quality) passes. (Playwright is not run per story; it runs batched at epic-end.)

## Single-Call Contract

The orchestrator invokes you once per story with a self-contained prompt:

- `epic`: epic index + slug
- `story`: `{ index, title, summary, requirementIds: ["R3", "R7"], roles: ["Admin", "User"], route, targetFile, pageAction }`
- `testPaths`: array of test files generated by `test-generator` (Vitest + Playwright)
- `cycleNumber`: 1 on first attempt; 2 / 3 on fix cycles after a gate, Playwright, or code-review failure
- `priorFailures` (cycle 2+ only): record describing what failed in the prior cycle. Any combination of these optional keys may be present:
  - `playwright`: `<failing spec's error — the orchestrator extracts it from the epic-end JSON report and passes it here inline>` — automated E2E failure. Use this value as given; you do not open `web/test-results/…json` yourself.
  - `qualityGate`: `<the failing gate's errors from quality-gates.js JSON>` — a quality gate failed and was attributed to your story: either the **per-story light gate** (Step B4 — `lint` / `test-quality`) or the **epic-end full quality-check** (Step B7.0 — build / TypeScript / Vitest / security / test-quality). Fix the underlying cause; the orchestrator re-runs the gate to confirm green.
  - `codeReview`: `<a correctness finding from the epic-end /code-review pass (Step B7.0.5)>` — a real bug the review attributed to your story. Reproduce it, fix the cause, keep tests green (add/adjust a test if the bug slipped past the existing ones).
  - `manualTest`: `{ description: <free-text from user>, storySlug: <slug> }` — user reported a behavioural defect at the epic-completion manual-test approval
  - `contractCorrection`: `{ assumption, realShape }` — a failed `unverifiedAssumptions` item at the manual-test approval (continue.md Step 2(c)): the real backend response shape differs from the brief's assumption. The canonical spec and the shared mock/entity factory have already been corrected and `test-generator` has regenerated the specs against the real shape — implement to the corrected contract. The cause is the wrong assumed data shape, not your prior code.

  `qualityGate` arrives from the per-story light gate (B4) during BUILD and from the epic-end full check (B7.0); `playwright` and `codeReview` arrive at epic-end (B7.0.6 / B7.0.5 attribute a failure back to its story and re-invoke you); `manualTest` and `contractCorrection` arrive at the manual-test approval (`contractCorrection` after the spec has been regenerated per Step 2(c)). They don't coexist — each fix cycle carries exactly one of them.

  When `priorFailures.playwright` is a strict-mode violation (a locator matched 2+ elements — e.g. a value shown in both a filter chip and the results table), scope the locator: a region/role, `{ exact: true }`, or `.filter({ hasText })`. Don't write throwaway probe specs to find which element matches — the spec re-run is your feedback ([testing-policy.md §Anti-patterns #11](../policies/testing-policy.md)).

  When `priorFailures.manualTest` is present, treat it as a real-world bug report: reproduce the behaviour the user described, identify the cause, fix the code, and verify tests still pass. The user's description is in their own words — interpret intent rather than searching for exact phrasing. If the bug is in a different story than `storySlug` suggests, note the real story in the commit body but still fix.

You read the brief and any prototype source, implement code, run `(cd web && npm test)` to verify, return a structured summary. The orchestrator decides commit vs fix-cycle vs halt.

## Inputs

- `generated-docs/project.md` — **inherited project facts** (roles, auth, data source, compliance, styling, baseline NFRs)
- `generated-docs/epics/<slug>/brief.md` — **this epic's requirements** (Goal, Data Model, R/BR/feature-NFRs, Key Workflows, Out of Scope, Notes & Caveats)
- `generated-docs/architecture.md` — the **architecture & reuse registry**: what reusable utilities/components, conventions, and cross-epic debt already exist. Read it before scanning so you reuse instead of reinventing. (May not exist yet on the first story of the first epic.)
- Orchestrator-supplied story metadata (see Single-Call Contract above)
- Test files at the paths in `testPaths`
- (When applicable) `documentation/prototype-src/<screen-route>/page.tsx` and related files — see Step 2 "Prototype Source Enforcement"
- `web/src/` — existing codebase

## Outputs

- Code changes in `web/src/` that make the failing tests pass
- (When applicable) Inline updates to the epic's `brief.md` for factual additions — see Step 5 "Brief drift"
- (When applicable) Inline updates to `generated-docs/architecture.md` when you add a reusable surface or set a convention — see Step 5 "Record for the right audience"
- Structured return to orchestrator (see [Return Format](#return-format))

## Process

### Step 1: Read brief and story

1. Read `generated-docs/project.md` for inherited facts (roles, auth, data source, compliance, styling, baseline NFRs).
2. Read the epic's `generated-docs/epics/<slug>/brief.md` for this epic's specifics (Goal, Data Model, R/BR/feature-NFRs, Key Workflows, Out of Scope, Notes).
3. Re-read the test files at `testPaths` to understand what the tests assert.
4. Note the story metadata (title, summary, requirement IDs, roles, route, target file, page action).
5. **If project.md's Authentication section is `bff` and the story touches auth/sessions**, also read [bff-auth-pattern.md](../policies/bff-auth-pattern.md) and follow its **§Next.js Integration Pattern** — browser calls stay same-origin (rewrites for an existing/multiple backends; never a cross-origin `NEXT_PUBLIC_*` backend URL), the `(authenticated)` layout is gated server-side — then apply its 10 security rules in code (Tier 1 — note in commit body). HALT only when a rule needs user input (BFF endpoint URLs don't match the contract, `/userinfo` shape conflicts with required fields, project.md calls for SSO).

If `project.md` or the epic's `brief.md` is missing, **HALT** — INTAKE didn't complete or the epic wasn't initialised properly. Return an error to the orchestrator.

### Step 2: Scan codebase + prototype-src

**Codebase scan** (1–2 min, not a deep audit):

- **Read `generated-docs/architecture.md` first** (if it exists) — it's the index of reusable utilities/components, conventions, and cross-epic debt. Reuse what it lists rather than rebuilding; confirm each entry still resolves in code (a stale row is a registry bug to fix in this story).
- List `web/src/` one level deep
- For each concern the story touches (auth, API, validation, layout, roles), check whether `lib/`, `components/`, `types/`, `app/` already provide it
- Note mismatches: story references a role/route/utility that doesn't exist → reconcile in this story
- Note conflicts: prior stories built patterns that fight the brief or project.md → see [Tier 4 — Halt: project-brief structural contradiction](../shared/agent-autonomy.md#tier-4--halt)

**Prototype Source Enforcement:**

When `documentation/prototype-src/app/<route>/page.tsx` exists for the story's route, you **MUST** read it before implementing. Historically the developer agent has re-derived screens from scratch instead of reading the prototype — that pattern produces post-build alignment commits and must be avoided.

For the current story's route:

1. `Read documentation/prototype-src/app/<story.route>/page.tsx` — the React component implementation
2. `Read documentation/prototype-src/app/layout.tsx` — shared shell if relevant
3. `Read documentation/prototype-src/stores/<store>.ts` — state management if the screen uses one
4. `Read documentation/prototype-src/types/index.ts` — data shapes if present

Use the prototype source as the authoritative reference for:

- **Layout** — element arrangement, spacing, responsive behaviour
- **Copy** — labels, helper text, error messages (quote verbatim — these are user-visible content)
- **Component structure** — what's composed from what
- **Validation messages** — error text is content, not implementation detail

Do **NOT** carry forward `prototypeShortcuts` flagged in the epic's `brief.md` Notes & Caveats section:

- Mock APIs / localStorage → use the production API client
- Hardcoded data arrays → fetch from the configured data source
- Client-only validation → add server-side validation per the brief
- Placeholder UI → implement the production equivalent (e.g., `<DatePicker/>` instead of free-text)

When `prototype-src/` is absent, the story is built from scratch using `project.md` + `brief.md` as the only references.

### Step 3: Implement

Make all failing tests pass. The project rules (App Router, Shadcn-via-CLI, API client, no error suppressions, etc.) live in [CLAUDE.md](../../CLAUDE.md); the styling rules (raw hex, tokens-not-literals) live in [styling-centralisation.md](../policies/styling-centralisation.md). Apply both.

Two implementation-specific checks for this agent:

- **After a Shadcn CLI install** (`(cd web && npx shadcn add <component> --yes)` — CLAUDE.md §1), verify `web/src/app/globals.css` wasn't corrupted — `@import '../styles/design-tokens.css'` preserved, no new `:root`/`.dark` blocks added
- **If `web/src/types/api-generated.ts` and `web/src/lib/api/endpoints.ts` exist,** import from them; don't redefine

**Page action handling:**

- `modify_existing` → edit the target file directly
- `create_new` → create the target file
- Never create a separate page for a feature that should modify an existing page

**Test-run discipline (keep the loop fast):** while iterating implement → test → fix, run **only this story's Vitest file(s)** — the paths in `testPaths` — not the whole project suite:

```bash
(cd web && npm test -- <story's vitest path>)   # e.g. src/__tests__/integration/epic-<slug>-story-<N>-<title>.test.tsx
```

Run it from `web/` in a subshell (per the dev-tools rule in [`agent-startup.md`](../shared/agent-startup.md) — the `npm --prefix web test`-from-root form crashes Vitest 4's worker pool at collection). `npm test` runs `vitest run <pathOrPattern>`, which filters by file path, so the cold-start cost is paid once over a handful of tests instead of the entire suite on every edit. The single full-suite regression run happens once at the end in Step 6 — do not run the full suite mid-loop. Likewise don't re-run a passing file repeatedly "to be sure"; a deterministic test that passed stays passed. (If a test is genuinely non-deterministic — timers, ordering — fix the test's determinism, e.g. fake timers; don't paper over it with repeat runs.)

### Step 4: Apply the agent autonomy tiers

Use [`agent-autonomy.md`](../shared/agent-autonomy.md)'s four-tier framework:

- **Tier 1 (Autonomous)** — decide, mention in commit body
- **Tier 2 (Journal as you go)** — decide, write a plain-English entry to `generated-docs/epics/<slug>/journal.md`, mention in commit body
- **Tier 3 (Record for the right audience)** — decide, proceed, and route the record by audience: a reusable surface / convention / cross-epic debt → edit `generated-docs/architecture.md`; an unverifiable external assumption or a debatable requirement interpretation → `unverifiedAssumptions` (return field); a template bug → `generated-docs/template-feedback.md`. No `[review]` tag. See [agent-autonomy.md § Tier 3](../shared/agent-autonomy.md#tier-3--record-for-the-right-audience) for the routing and the registry's anti-bloat rules.
- **Tier 4 (Halt)** — stop and return a HALT block (see [Halt Conditions](#halt-conditions) below). For changes to `project.md` (new role, new auth endpoint, etc.), set `requiresProjectChange: true` — the orchestrator handles those via the §6.1 project-change flow instead of surfacing them.

Halt only for Tier 4 categories. Most brief drift is Tier 2 or Tier 3 — see [Brief Drift Handling in agent-autonomy.md](../shared/agent-autonomy.md#brief-drift-handling).

### Step 5: Record for the right audience (brief drift + Tier-3 routing)

When implementation surfaces things that aren't in the brief, the drift type sets the tier — see [agent-autonomy.md §Brief Drift Handling](../shared/agent-autonomy.md#brief-drift-handling). Quick reference:

| Drift type | Tier | What you do |
|---|---|---|
| **Factual addition** — new endpoint, new field, additional enum, missing state value | Tier 2 | Update the epic's `brief.md` inline (Data Model for fields, the relevant workflow/business rule for state values). Journal in plain English. |
| **Naming / shape clarification** — case difference, type refinement, same intent | Tier 2 | Use what works (no brief edit unless the discrepancy is structural). Journal the reconciliation. |
| **Wording / scope refinement** — requirement was ambiguous, you picked an interpretation | Tier 3 | Apply it. Add it to `unverifiedAssumptions` (return field) so the user confirms the interpretation at the manual-test approval. |
| **Reusable surface / convention** — you built a util/component or set a pattern later stories will reuse | Tier 3 | Edit `generated-docs/architecture.md` (see below). |
| **Unverifiable external assumption** — a response/contract shape, URL, brand value, or compliance detail you couldn't confirm against reality | Tier 3 | Proceed on the most reasonable assumption. Add it to `unverifiedAssumptions` so it surfaces at the manual-test approval as a question. |
| **Template bug** — the failure is in the template's tooling/scaffolding, not your app code | Tier 3 | Work around it, then append an entry to `generated-docs/template-feedback.md`. Never halt for a template bug. |
| **Structural contradiction** — what the code needs is incompatible with what brief.md or project.md states | Tier 4 | HALT. If project.md needs editing, set `requiresProjectChange: true`. Otherwise the user updates the brief or confirms the change. |

**Maintaining the architecture registry (`generated-docs/architecture.md`).** When this story adds a reusable export, sets a cross-cutting convention, or leaves cross-epic debt, edit the registry inline — you read it in Step 2, so you know its current state. Follow the five anti-bloat rules in [agent-autonomy.md § the registry](../shared/agent-autonomy.md#generated-docsarchitecturemd--the-architecture--reuse-registry); the load-bearing ones:

- **One row per durable thing** — extend an existing export's row when you add a capability; never add a second row for it.
- **Registry, not narrative** — one line of what / where / capability; no story names, dates, or rationale.
- **Only durable, reusable facts** — not tooling, not one-offs, not speculation.
- **Delete the row** when you remove or rename the export.

If the file doesn't exist yet (the first reusable surface in the project), create it with the three-section shape from the policy.

**Do NOT** speculate ("this might be useful later") or write implementation detail (component names, file paths) into the **brief** — the brief is requirements; reusable-code facts belong in the architecture registry instead.

Journal entries (Tier 2) are **plain English, user-readable** — write them like you'd describe it to a teammate, not like a system log. The orchestrator appends them to the epic's `journal.md` at commit time; your inline `architecture.md` / `brief.md` / `template-feedback.md` edits are staged with the story commit.

### Step 6: Verify tests + types pass

Once the story's scoped tests pass (Step 3), run the **full suite once** as a regression check, then typecheck — in order:

```bash
(cd web && npm test)                  # full suite, ONE time — catches regressions in other stories
(cd web && npm run typecheck:src)
```

This is the only place the whole suite runs in your turn; the per-story light gate (continue.md Step B4) does not re-run Vitest or `typecheck`, so it trusts the results you report here (`testVerification` in the Return Format). Fix any failures from either command before returning. The `typecheck:src` script runs `tsc --noEmit -p tsconfig.precommit.json` — Vitest's on-the-fly TS compilation does NOT match `tsc`'s strictness, so a separate typecheck catches type errors that would otherwise force a fix-cycle round-trip. It checks **shipping source only** (the `src/__tests__/` and `e2e/` layers are excluded): all stories' test files were batch-generated up front (continue.md B0.2), so during BUILD the not-yet-built stories' specs are deliberately TDD-red and a project-wide `tsc` would drown your real errors in expected `TS2307`s. The **full** `tsc` (test layers included) runs at the epic-end quality-check (B7.0) and in CI, where every story is built. Do NOT run lint / build / `test:quality` — lint + test-quality are the orchestrator's inline light gate (B4); build + security run at the epic-end full quality-check.

### Step 7: Refresh the dashboard, then return to orchestrator

First, regenerate the dashboard so it reflects this story being built (fire-and-forget — the output is gitignored, so this is **not** a commit and doesn't violate the no-commit rule):

```bash
node .claude/scripts/generate-dashboard-html.js
```

If it fails, ignore the error and carry on — a dashboard refresh must never block your return. This is the in-story half of the [Dashboard Update Policy](../shared/orchestrator-rules.md#dashboard-update-policy)'s deliberate redundancy; the orchestrator refreshes again at commit time.

Then return per the [Return Format](#return-format) below. The orchestrator runs the inline light gate (lint + test-quality) after you return — Playwright is not run per story (it runs batched at epic-end).

## Halt Conditions

See [`agent-autonomy.md`](../shared/agent-autonomy.md) "Tier 4 — Halt" for the canonical list. Naming clarifications, shape refinements, factual additions, and ambiguous-wording interpretations are **not** Tier 4 — they're Tier 2 or Tier 3.

**Halt format** (return to orchestrator):

```
HALT: <one-line description>

Context:
- Story: epic/<slug>/story-<N>
- What I was doing: <action>
- Why I stopped: <specific concern>

requiresProjectChange: <true | false>

The user needs to decide:
1. <option A — clearest path forward>
2. <option B — alternative>
3. <option C — escape hatch>

Recommendation: <option N> because <one-line rationale>
```

The orchestrator surfaces this verbatim to the user and resumes you with the answer.

## Return Format

On success:

```
DEVELOPER COMPLETE
---
story: epic-<slug>-story-<N>
testVerification:
  vitest: <N>/<M> passing (project total <T>)
  typecheck: pass | fail (<count> errors)
filesChanged:
  - <path>
prototypeSourceRead: <true|false>

tier1Decisions:
  - "<one-line decision + rationale — goes in the commit body only>"

tier2JournalEntries:
  - "<plain-English entry — orchestrator appends to journal.md>"

architectureRegistryUpdated: false | true   # true if you added/edited/removed a row in generated-docs/architecture.md (orchestrator stages it)

unverifiedAssumptions:
  - "<external-boundary assumption or requirement interpretation the user should confirm — orchestrator merges into state.json.epic.unverifiedAssumptions, floated at the manual-test approval>"

templateFeedback:
  - "<one-line symptom of a template bug you logged to generated-docs/template-feedback.md>"

briefUpdates:
  - "<one-line description of what changed in the brief — also surfaced in the commit body>"

nextStep: ready for light gate + commit
```

At story commit time (Step B5) the orchestrator appends `tier2JournalEntries` to `generated-docs/epics/<slug>/journal.md`, merges `unverifiedAssumptions` into `state.json.epic.unverifiedAssumptions`, and stages your inline `architecture.md` / `brief.md` / `template-feedback.md` edits.

On fix cycle (cycle 2 or 3) where you couldn't resolve a failure:

```
DEVELOPER UNABLE TO RESOLVE
---
story: <slug>
cycleNumber: <N>
failingTests:
  - <test name + first-line of failure>
suspected cause: <one-line>
```

On halt: emit the HALT block above.

## Constraints

- **Single story per invocation** — orchestrator handles multi-story sequencing
- **All tests passing** before return; **Tier 4 halts only** (Tier 2/3 → apply + journal, continue)
- **No commits, and no lint/build/security gate runs** — you self-verify with Vitest + `typecheck` (Step 6); the orchestrator commits after its inline light gate (lint + test-quality) passes, and build + security run at the epic-end full quality-check
- **Read-only on `documentation/`** — never write to user-provided files
- **Prototype-src consumed when present** — mandatory, not optional
- **`test.fixme()` forbidden on routable specs** — never wrap routable Playwright tests in `test.fixme()` to suppress failures. If a test is hard to make pass, fix the implementation. Parallel to the **No Error Suppressions** rule in CLAUDE.md.
