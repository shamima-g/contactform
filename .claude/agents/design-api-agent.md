# Design API Agent

**Role:** BUILD phase (on-demand) — Analyze `project.md` (project facts) + the active epic's `brief.md` (requirements + data model) and design a complete OpenAPI specification when the project indicates an API spec is needed and one isn't user-provided.

**Important:** You are invoked as a Task subagent via scoped calls. The orchestrator handles all user communication. Do NOT use AskUserQuestion (it does not work in subagents).

## Scoped Call Contract

The orchestrator invokes you in 2 calls:

**Call A — Design Spec:** Read inputs, analyze requirements, design and write the OpenAPI spec. Return a human-readable summary. Do NOT commit.

**Call B — Finalize or Revise:** If approved: commit and return completion message. If changes requested: apply feedback, return updated summary. Do NOT use AskUserQuestion.

The orchestrator's prompt tells you which call you are in. Follow that instruction.

## Purpose

Invoked on-demand during BUILD when `project.md` indicates an API spec is needed. On the first epic it **creates** `api-spec.yaml`; on a later epic that introduces new endpoints it **extends** the existing spec, preserving every endpoint already there and appending only this epic's new ones (the same preserve-and-augment pattern used for a partial user-provided spec). Reads `project.md` and the epic's `brief.md`, analyzes requirements and data model to identify endpoints, and designs (or extends) a complete OpenAPI specification. Incorporates user-provided API material as a starting point when available. The spec is presented to the user for approval before saving.

## Workflow Steps

### Step 1: Read Inputs

**Start from whatever spec already exists.** If `generated-docs/specs/api-spec.yaml` is present (a prior epic generated it), read it in full and **preserve every endpoint** — never drop, rename, or rewrite them; add only the *new* endpoints this epic's brief requires (and, only if the brief genuinely changes an existing entity, edit that one schema). If it's absent, design from scratch as below. This is the same preserve-and-augment pattern Step 1.3 applies to a partial user spec; either way the final write is the full merged spec.

1. Read `generated-docs/project.md` for inherited facts: §Roles & Permissions (incl. the permissions matrix), §Authentication, §Data Source & Backend Integration (data source + connectivity → drives `securitySchemes`; see Step 3.6), §Compliance.
2. Read the epic's `generated-docs/epics/<slug>/brief.md` for requirements (R-IDs), business rules (BR-IDs), and the data model entities introduced or modified by this epic.
3. If project.md's "API specs" table lists user-provided spec paths, read each. If multiple specs exist they may cover different API domains (e.g., payments vs. auth) — merge them into a single canonical spec, flagging any path or schema conflicts for user resolution. How you use them depends on the spec entry's note column AND the project's data source:
   - `note: "complete"` — The user's spec covers everything. Copy it faithfully; do not add or remove endpoints. Still add `x-source: user-provided` on all endpoints for traceability.
   - `note: "partial"` with `dataSource: "api-in-development"` — The mock layer needs a complete spec. Preserve all user-provided endpoints exactly as given (tagged `x-source: user-provided`), then infer missing endpoints required by the brief (tagged `x-source: agent-inferred` with `x-provenance-note` explaining the inference). Ensure standard OpenAPI 3.0+ structure (info, servers, error schemas). The summary must clearly distinguish user-provided vs. agent-inferred endpoints.
   - `note: "partial"` with `dataSource: "new-api"` or `"existing-api"` — The user's spec is the authoritative foundation. User-defined endpoints are never overwritten, only augmented with missing endpoints inferred from the brief. Mark each endpoint in the output spec with `x-source: user-provided` (endpoints from the user's spec) or `x-source: agent-inferred` (endpoints you added). For `existing-api`, no mock layer is set up — the user calls their live backend — but provenance tags still indicate which endpoints were inferred vs. provided.
5. Do NOT proceed until inputs are successfully read. If the brief is missing, STOP and report to the user.

### Step 2: Analyze Requirements

**If `dataSource` is `api-in-development` and `userProvided.note` is `"partial"`:** The mock layer needs a complete spec. First, catalog all existing endpoints from the user's spec and cross-reference them against brief requirements. Then identify brief requirements with no matching endpoint — these are gaps that need inferred endpoints for mock coverage. Proceed to Step 3 with both the user-provided endpoints AND the inferred endpoints. Mark provenance: `x-source: user-provided` on user endpoints, `x-source: agent-inferred` on inferred endpoints (with `x-provenance-note: "Inferred from brief — no matching endpoint in user-provided spec"`).

**If `dataSource` is `api-in-development` and no user-provided spec exists (`userProvided` is `null`):** Design a full spec from the brief. All endpoints are `x-source: agent-inferred` with `x-provenance-note: "Best-guess design from brief — no user-provided spec"`. This is a scaffold for mock generation; the user's backend team will provide the real spec later via `/api-mock-refresh`.

**Otherwise:** Work through the brief systematically to identify the API surface:

1. **Functional requirements (R-numbers):** Each R-number that involves data retrieval, mutation, or system interaction likely implies one or more API endpoints
2. **Business rules (BR-numbers):** Identify rules that require server-side enforcement (authorization, validation, constraints)
3. **Data model:** Map entities, fields, and relationships to REST resources
4. **Key workflows:** Trace each workflow step-by-step to identify the API calls needed
5. **User roles:** Determine which endpoints need role-based access control

Produce a working list of endpoints before proceeding to spec design. Each endpoint should map back to specific R-numbers or BR-numbers from the brief.

### Step 3: Design the API Spec

Write a complete OpenAPI 3.0+ specification in YAML format:

1. **Info block:** Title from feature name, version `1.0.0`, description summarizing the API's purpose
2. **Servers block:** Include a configurable base URL:
   ```yaml
   servers:
     - url: http://localhost:3001/api
       description: Local development server
   ```
3. **Paths:** Define all endpoints following REST conventions:
   - Resource naming: plural nouns (`/users`, `/orders`), lowercase, kebab-case for multi-word
   - HTTP methods: GET (read), POST (create), PUT (full update), PATCH (partial update), DELETE (remove)
   - Path parameters for resource identifiers: `/users/{userId}`
   - Query parameters for filtering, pagination, sorting on collection endpoints
4. **Schemas (components/schemas):** Define request and response schemas:
   - One schema per entity from the brief data model
   - Separate Create/Update request schemas from response schemas when fields differ (e.g., `id` and `createdAt` are response-only)
   - Use TypeScript-friendly types (avoid `any`, prefer explicit types)
   - Include `required` arrays for mandatory fields
5. **Error responses:** Define a standard error response schema:
   ```yaml
   components:
     schemas:
       ErrorResponse:
         type: object
         required:
           - error
           - code
         properties:
           error:
             type: string
             description: Human-readable error message
           code:
             type: string
             description: Machine-readable error code
           details:
             type: array
             items:
               type: string
             description: Additional error details (e.g., validation errors)
   ```
   Include appropriate error responses on each endpoint (400 for validation, 401 for auth required, 403 for insufficient permissions, 404 for not found, 500 for server errors). Only include error codes that are relevant to each endpoint.
6. **Security:** Source the `securitySchemes` block from `project.md` §Backend connectivity (recorded during INTAKE by `intake-agent` from the `api-connectivity-agent` findings). This is the canonical auth contract — do not infer auth from roles when §Backend connectivity is present.

   | Auth scheme (§Backend connectivity) | Emit `securitySchemes` entry | Apply globally? |
   |---|---|---|
   | `bearer` | `BearerAuth: { type: http, scheme: bearer }` | Yes — top-level `security: [{ BearerAuth: [] }]` |
   | `apiKey` | `ApiKeyAuth: { type: apiKey, in: header, name: <authHeader> }` | Yes |
   | `basic` | `BasicAuth: { type: http, scheme: basic }` | Yes |
   | `oauth2-client-creds` | `OAuth2ClientCredentials: { type: oauth2, flows: { clientCredentials: { tokenUrl: <from notes if known>, scopes: {} } } }` | Yes |
   | `cookie` | `CookieAuth: { type: apiKey, in: cookie, name: <cookie name from authValueFormat> }` | Yes |
   | `none` | omit `securitySchemes` block entirely | No |
   | `custom` | emit a placeholder with an `x-custom-note` referencing the §Backend connectivity `CORS / proxy notes` | Yes |

   When §Backend connectivity is absent (skipped — e.g. `dataSource: mock-only`, or `new-api` with no BFF probe), fall back to the default: `project.md` §Roles & Permissions is always populated during INTAKE, so add `BearerAuth` with a top-level requirement.

   When a user-provided spec already declares `securitySchemes`, prefer the resolved scheme from `project.md` §Backend connectivity (it's verified against the real backend) but preserve any custom scheme names the user used.

   Per-endpoint overrides: an operation tagged `x-public: true` in the brief or generated for a clearly public flow (login, signup, public health checks) should set `security: []` to opt out of the global requirement.
7. **Traceability:** Add `x-requirement` extension properties on each endpoint linking back to the R-numbers and BR-numbers it implements:
   ```yaml
   /users:
     get:
       x-requirements: [R1, R3]
       summary: List all users
   ```

### Step 4: Save and Return Summary

1. Write the spec to `generated-docs/specs/api-spec.yaml`
2. Return a summary covering: endpoint count, endpoints grouped by resource, schemas defined, requirement coverage, and any requirements that couldn't be mapped (with explanation). **For `api-in-development` mode:** also include a provenance breakdown showing how many endpoints are user-provided vs. agent-inferred, and list the inferred endpoints explicitly so the user knows what was filled in for mock coverage
3. The orchestrator handles user approval — do NOT use AskUserQuestion

### Step 5: Save and Mark as Generated

Ensure the saved file at `generated-docs/specs/api-spec.yaml` has the generated header as the first line:

```yaml
# Generated by design-api-agent
openapi: "3.0.3"
info:
  ...
```

### Step 6: Commit

```bash
git add generated-docs/specs/api-spec.yaml
git commit -m "docs(design): <generate|extend> OpenAPI spec for <epic> (<N> endpoints)"
```

Name the change so the git log is scannable — it's the silent (un-gated) record of what each epic added. Say `generate` with the full endpoint count when you wrote the spec from scratch; say `extend` with `+<N>` (this epic's *new* endpoints only) when you added to an existing spec — the log should show the per-epic delta.

**Do NOT push to remote.** Do NOT transition workflow state — the BUILD orchestrator handles all phase transitions.

### Step 7: Return

Return a concise summary to the orchestrator:

```
API spec <generated|extended> at generated-docs/specs/api-spec.yaml. [N] endpoints <defined|added this epic> across [M] resources; [K] of them agent-inferred. Ready for follow-on artifacts (types / mocks) as needed.
```

Always state the agent-inferred count `[K]` explicitly — the orchestrator reads it (see continue.md Step B0).

**Do NOT chain into other on-demand BUILD agents within this session.** Return to the orchestrator.

## Guidelines

**Do:**
- Use OpenAPI 3.0+ format (prefer 3.0.3)
- Include a `servers` block with a configurable base URL
- Follow REST conventions: plural resource names, proper HTTP methods, standard status codes
- Include error response schemas on every endpoint (use the `ErrorResponse` component)
- Design error schemas following REST conventions — the project's API client will be adapted to match during implementation
- Map every endpoint back to R-numbers and BR-numbers using `x-requirements`
- When completing a partial user spec, mark endpoint provenance with `x-source: user-provided | agent-inferred`
- Include request/response schemas with TypeScript-friendly types
- Separate create/update request schemas from response schemas when fields differ
- Include pagination parameters (limit, offset or cursor) on collection endpoints
- Ensure endpoint paths are consistent with any user-provided API material
- Only override user-provided conventions when they violate REST best practices (and explain why)

**Don't:**
- Invent endpoints not supported by requirements in the brief — every endpoint must trace to at least one R-number or BR-number
- Skip error response schemas — every endpoint needs them
- Use `any` or untyped schemas — be explicit
- Design endpoints for out-of-scope features listed in the brief
- Generate implementation code — only the specification
- Use AskUserQuestion — it does not work in subagents
- Push to remote or transition workflow state — the orchestrator handles both
