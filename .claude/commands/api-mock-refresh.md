# /api-mock-refresh

Run this command when your backend developer has updated the API spec and you need the mock handlers to reflect the changes.

## What this does

- Detects what changed between the current spec and the snapshot from the last generation
- Updates the canonical spec if the source spec has changed
- Regenerates only the affected handlers — hand-curated data for unchanged endpoints is preserved
- Updates `mock-spec-snapshot.yaml` and `mock-data-context.md`

## Prerequisites

- Mock infrastructure must already be set up (i.e. `web/src/mocks/` exists and `mock-spec-snapshot.yaml` exists in `generated-docs/specs/`)
- If mock setup hasn't been done yet, this is not the right command — `mock-setup-agent` is invoked from the BUILD bootstrap (continue.md Step B0.1) when `api-spec.yaml` exists and `project.md` §Data Source needs a mock layer (`dataSource` = `mock-only` or `api-in-development`)

---

## Steps

### Step 1 — Read Prerequisites

Read all files in parallel:
- `generated-docs/specs/api-spec.yaml` — canonical spec
- `generated-docs/specs/mock-spec-snapshot.yaml` — snapshot from last generation
- `generated-docs/specs/mock-data-context.md` — data conventions
- `generated-docs/project.md` — project facts including Data Source / Backend Integration (needed for Step 2)
- `web/src/mocks/handlers.ts` — existing handlers

If any of these reads fail (file not found), stop and tell the user: "Mock infrastructure doesn't appear to be set up yet. This command is for updating an existing mock layer. `mock-setup-agent` runs from the BUILD bootstrap when the project's data source needs a mock layer (`dataSource` = `mock-only` or `api-in-development`) and `api-spec.yaml` exists."

### Step 2 — Check for Source Spec Updates

Check project.md §Data Source → §API specs (read in Step 1) for rows whose Source is `user-provided`. If one or more exist, use the first listed `Path` as the primary source spec; read all of them — the canonical `api-spec.yaml` was merged from all of them when `design-api-agent` first ran, so use the first as the primary comparison source. If none are user-provided, fall back to scanning `documentation/` for any `.yaml` or `.json` file with OpenAPI/Swagger content.

If no source spec is found (common when the spec was fully generated by design-api-agent), skip to Step 3.

If a source spec is found, read it and compare its contents against the canonical `generated-docs/specs/api-spec.yaml` (already in memory from Step 1).

If they differ, ask the user using `AskUserQuestion`:
- "I found an updated spec at `documentation/<spec-file>`. Should I update the canonical spec from it before refreshing the mock handlers?"
- Options: "Yes, update from source" / "No, use the existing canonical spec as-is"

If "Yes": reconcile `x-source` tags and adopt the user's schema into the canonical spec:

1. For each endpoint in the user's source spec: set `x-source: user-provided` in the canonical spec and adopt the user's schema (request params, request body, response schema). This applies to both new transitions (`agent-inferred` → `user-provided`) and existing `user-provided` endpoints whose schema has changed.
2. For endpoints in the canonical spec that are NOT in the user's source spec: keep them with `x-source: agent-inferred` (still needed for mock coverage).
3. For endpoints that transition from `agent-inferred` → `user-provided`: if the schema changed, flag this in the changeset summary so the user knows the mock contract shifted.
4. For endpoints already `user-provided` where the schema changed: flag as "schema updated" in the changeset.

Write the reconciled result to `generated-docs/specs/api-spec.yaml`.

### Step 2.5 — Check for `securitySchemes` Drift

**Skip this step entirely** when `project.md` §Backend connectivity is missing, blank, or Shape 1 (smoke-test skipped).

When connectivity was captured during INTAKE, compare the canonical spec's `securitySchemes` block (post-Step 2 reconciliation) against the §Backend connectivity `Auth scheme` / `Auth header` in project.md. That captured config is the verified contract; if the spec now declares something different, the captured config (and the saved `api-smoke-test.sh`) is stale.

Drift cases:

| Spec scheme (after Step 2) | §Backend connectivity `Auth scheme` | Treat as |
|---|---|---|
| matches captured | matches | No drift — proceed to Step 3 |
| different scheme (e.g. `bearer` → `apiKey`) | older value | **Drift** |
| spec has no security | captured has a scheme | **Drift** — backend dropped auth |
| spec adds security | captured is `none` | **Drift** — backend added auth, smoke test now hits protected endpoints |

When drift is detected, do NOT auto-update project.md. Use `AskUserQuestion`:
- Question: "The updated spec declares `[new scheme]` auth, but the captured §Backend connectivity `Auth scheme` is `[old scheme]`. The captured smoke test and any auth-aware client wiring still reference the old scheme."
- Options:
  - "Re-run /api-status --check after I update .env.local" (Recommended) — list the env var names from the §Backend connectivity `Credential env vars` row so the user knows what may need new values; continue to Step 3 without modifying project.md. Record this for Step 5's summary.
  - "Update the §Backend connectivity auth rows only" — overwrite `Auth scheme`, `Auth header`, `Auth value format` from the new spec; leave `Credential env vars` and `Smoke-test endpoint` as-is; set `Smoke-test status: null-deferred` and clear `Smoke-test verified at` (the old verification no longer applies); set `Smoke-test notes: "Auth scheme drift detected during /api-mock-refresh — re-run /api-status --check to verify."`
  - "Ignore — spec is sloppy, real auth unchanged" — log the divergence for Step 5's summary; no project.md changes

### Step 3 — Diff Snapshot vs Current Canonical Spec

Read both files and compare their `paths` sections to produce a changeset.

**Endpoint matching rules:**

- **Match key:** HTTP method + normalized path template
- **Parameter name normalization:** `GET /v1/users/{id}` and `GET /v1/users/{userId}` are the **same endpoint** (parameter names differ but path shape matches). Normalize by replacing all `{paramName}` segments with `{_}` before comparing.
- **Trailing slashes:** Ignored — `/users/` matches `/users`
- **Query parameters:** NOT part of the match key (compared as schema changes within a matched endpoint)

**Diff categories:**

| Category | Definition | Handler action |
|----------|-----------|---------------|
| **Added** | In canonical spec but not in snapshot | Generate new handler |
| **Removed** | In snapshot but not in canonical spec | Remove handler |
| **Schema changed** | Same method+path, but request params, request body, or response schema differs | Regenerate handler (preserve custom data where possible) |
| **Metadata only** | Same method+path+schema, but `x-source`, `x-requirements`, or `description` changed | No handler change needed |
| **Unchanged** | Identical in both | Skip |

Produce the changeset:

```
CHANGESET
---
added:
  - [METHOD] [path]
changed:
  - [METHOD] [path] — [what changed: request params, response schema, etc.]
removed:
  - [METHOD] [path]
metadata_only:
  - [METHOD] [path] — [what metadata changed, e.g. "x-source: agent-inferred → user-provided"]
unchanged:
  - [count] endpoints unchanged
```

If there are no differences (or only metadata-only changes), tell the user: "No handler-affecting changes detected between the current spec and the last snapshot — handlers are already up to date." For metadata-only changes, still update the snapshot (Step 4) so drift detection stays clean. Stop if no handler changes are needed.

### Step 3.5 — Check Smoke-Test Endpoint Impact

**Skip this step entirely** when project.md §Backend connectivity is missing, blank, Shape 1 (smoke-test skipped), or when the §Backend connectivity `Smoke-test endpoint` does NOT appear in the changeset's `removed` list.

When the saved smoke-test endpoint is being removed, the artifact at `generated-docs/specs/api-smoke-test.sh` will 404 on next re-run (via `/api-status --check` or `/api-go-live`'s pre-flip gate). Pick a replacement using the same heuristic as `api-connectivity-agent`:

1. An explicit health endpoint: `GET /health`, `/healthz`, `/ping`, `/status`
2. A `GET` operation with no required path params and no required body (e.g. `/me`, list endpoints)
3. A `GET` operation with only optional query params

Use `AskUserQuestion`:
- Question: "Your smoke-test endpoint `[METHOD] [removed endpoint]` was dropped in this spec update. Suggested replacement: `[METHOD] [new endpoint]`. The saved `api-smoke-test.sh` will 404 on next re-run unless we update it."
- Options:
  - "Use the suggested replacement" (Recommended) — update the Smoke-test endpoint and verified-status rows in `project.md` §Backend connectivity, regenerate `generated-docs/specs/api-smoke-test.sh` with the new endpoint (preserving the existing auth-header substitution pattern), set Smoke-test status back to `null-deferred` until re-verified, add a warning row noting the change so `/api-status --check` re-runs.
  - "Pick a different endpoint" — open-ended plain-text prompt: "Which endpoint should be the smoke test? (path only, e.g. `/v1/orders`)" Then apply the same updates as above with the user's choice.
  - "Skip for now" — leave project.md and the artifact alone; record for Step 5's summary so the user is reminded the saved smoke test is now broken.

### Step 4 — Run mock-setup-agent and type-generator-agent

**Step 4a — Run mock-setup-agent (Call A, partial mode):**

Invoke the `mock-setup-agent` with this prompt:

> "This is Call A — Partial Handler Refresh. This is a /api-mock-refresh run, not an initial generation.
>
> Changeset from spec diff:
> [paste changeset from Step 3]
>
> Apply your partial-refresh rules (Step 2 in your instructions) to update only the affected handlers.
> Update mock-spec-snapshot.yaml with the current canonical spec. Add a `# Generated: <ISO-8601 timestamp>` header comment as the first line (e.g., `# Generated: 2026-03-06T14:30:00Z`). This timestamp is used by /api-status for "Last refresh" display.
>
> Do NOT create browser.ts, MockProvider.tsx, or modify layout.tsx — infrastructure is already in place.
> Do NOT commit. Do NOT use AskUserQuestion."

**Step 4b — Re-run type-generator-agent (conditional, parallel with Step 4a):**

**Condition:** Only run when `web/src/types/api-generated.ts` exists AND the changeset from Step 3 contains `added`, `changed`, or `removed` entries (skip for metadata-only or unchanged results).

Invoke `type-generator-agent` with this prompt:

> "This is a /api-mock-refresh regeneration. Read the updated canonical spec at generated-docs/specs/api-spec.yaml. Regenerate web/src/types/api-generated.ts and web/src/lib/api/endpoints.ts. Run `(cd web && npm run typecheck)` to verify. Do NOT commit. Do NOT use AskUserQuestion."

Since type-generator writes to `web/src/types/` and `web/src/lib/api/endpoints.ts` while mock-setup writes to `web/src/mocks/`, they have no file conflicts and can run in parallel.

### Step 5 — Report Results

After the agent returns, display a summary to the user:

```
Mock handlers refreshed.

Changes applied:
  Added:   [N] handlers
  Updated: [N] handlers
  Removed: [N] handlers
  Types regenerated: [N] interfaces, [M] endpoint functions

Provenance transitions:
  [N] endpoints transitioned from inferred → user-provided
  [N] user-provided endpoints had schema updates

Connectivity:
  ⚠️  Auth scheme drift: spec declares [new] but project.md §Backend connectivity still has [old] — [user-chosen action]
  ⚠️  Smoke-test endpoint updated: [old] → [new]. Re-run /api-status --check to verify.
  [or "ℹ️  Smoke-test endpoint left unchanged but [old endpoint] is now removed — saved api-smoke-test.sh will 404."]

Reminder: restart your dev server for the service worker to pick up the changes.
  (cd web && npm run dev)

Tip: run /api-status to see the updated endpoint provenance and coverage.
```

Omit sections that don't apply:
- **"Provenance transitions"** — if there were no `x-source` changes (e.g., when no source spec update was applied in Step 2)
- **"Types regenerated"** line — if Step 4b was skipped (no `api-generated.ts` existed)
- **"Connectivity"** — if project.md §Backend connectivity is missing/Shape 1 OR if no auth drift was detected and the smoke-test endpoint wasn't affected. Show only the lines that actually apply.

---

## Notes

- This command only updates handlers — it does not re-run browser infrastructure setup
- If you need to fully re-initialise the mock layer (e.g. after a `web/src/mocks/` directory was deleted), ask Claude to re-run the `mock-setup-agent` directly
- The `mock-spec-snapshot.yaml` is the source of truth for "what handlers were last generated from" — do not delete it
